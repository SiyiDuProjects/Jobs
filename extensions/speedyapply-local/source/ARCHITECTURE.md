# Autofill runtime contracts

These implementation contracts are enforced by the adapter, writer, ownership and submission tests. Operational permissions and delivery boundaries stay in the repository AGENTS.md.

- **A missed control** appears in the snapshot's `unrecognized` list (question, reason, tag/role/class outline) and as a local reproduction case. Make it readable in its layer: a site's structure in `src/custom/platform-config.js` declarations, a widget as a registered component (`describe`/`facts`, `readOptions`, `choose`) in the `control-fields.js` registry; standard ARIA comboboxes already use the fallback. Never add site branches to the scanner; all page clicks/events go through `JobsPageActions`.
- **Every adapter** (all 30 in `source/content/adapters/`) runs each page/step as one `JobsAutomatic.advance({fill})`. Adapters provide structure actions and ordered `JobsFormPipeline.bind` declarations (`name/find/answer`, `answers`, `checked/replace`, `after`) only; they never write answers, read options or call a resolver (`tests/one-answerer.test.mjs` checks every adapter). Sign-in fills use `jobsFillAccount` outside a run; step buttons come from `jobsStepNavigation`. Inside the run each binding is written in page order, then every remaining empty node is resolved at most once, conditional fields settle/rescan, then request-bound supplemental answers, review and navigation. A run keeps one field ledger (`JobsFormPipeline.ledger`: state, decider, confirm, card); every answer (binding, rule, AI, review card) reaches a field only through `JobsFormPipeline.write` (claim → write → kept by the page → decide or abstain), and a failure changes only that field's record. Optional supplemental fields accept only a verified `write`; unsupported optional questions remain empty without a review card. A canonical node has one automatic decider per run (the layer whose value it holds); a second claim must diagnose and fail. A binding or rule that cannot match or keep its value abstains; an unresolved choice is passed with its actual options to the server. Filling defaults never establish personal facts. `JobsFormPipeline.answered(root)` provides all automatically decided nodes excluded from saved manual responses, including AI and remote writes. Option writes use `optionSpec` through the sole `chooseSpec -> chooseFrom` transaction. Waits are conditions (`JobsFormPipeline.settled`, bounded `JobsDOMWait.until`), never fixed delays; an unconfirmed upload returns a hold and does not navigate. A new ATS is added the same way.
- **Shared Profile answers and option meanings.** `profile-question-types.js` recognizes supported question wording across platforms; `profile-answers.js` reads the explicit Profile facts, preserves country/date precision, and supplies option specifications. Canonical labels in `answer-vocabulary.json` and supported questions enter the same `answer-resolver.js` path. Known answers write automatically before requesting the server; missing facts, unsupported conditions or unmatched options retain AI fallback. No company-specific branches or keyword-memory answer engine belong here. Broader question recognition does not broaden deduplication of person answers. Components open, search, list, click and read back without reading the Profile. Structure such as an `educationIndex` belongs to adapters and components.
- **Server answers.** `JOBS_ANSWER_FLOW` selects `simple` or the retained `legacy` engine. Both return `answer`, `draft` or `unknown` with Chinese meanings and reasons to protocol 3 clients. The simple engine reads human-readable current Profile facts and all origins of similar saved answers. Recent person answers for exactly the same company/question/options may be reused directly. One model batch chooses remaining answers. Structural checks cover offered values, types and exact-date precision; there is no citation or semantic proof gate. The worker binds each response to its pinned Profile and field shape. Private caches include Profile/model/prompt/context and relevant saved-answer revisions; option labels are rebound to current page IDs. Unrelated saved-answer updates do not cancel the batch. Each invalid or stale row affects only itself.
- **Drafts and interruptions.** Valid `answer` values write through the single pipeline, remain visible with Chinese explanations, and do not block continuation. Unknown required questions, invalid answers and unsuccessful writes remain on the review surface. Optional unknowns remain blank. `draft` values are open text; in person mode they join the tab/Profile/version/job-bound final checklist. Changes invalidate checklist approval. Person corrections use the same pipeline; confirmation drains pending edits before continuation. Old flow dependencies and corpus mappings remain for rollback until separately approved retirement.
- **Learning ownership.** Only explicit person-origin answers enter saved responses. Agent and page-tool operations never become person-origin through trusted browser events. Records retain full question, operator origin, time, company/country/job context and original scope. Unknown legacy origin is not promoted; keywords and appearance counts are compatibility data only, not an answer engine. Client-side saved records never override the current Profile locally.
- **Behavior tests** protect every adapter and component; the historical comparison with the original bundle was retired on 2026-09-24.
- **Private question corpus.** `corpus-content.js` captures inert form trees before continuation and on person corrections. It never awaits upload or writes to the page. `corpus-case.js` removes form values, selection state, credentials, file names and matching identity text; actual option/search observations stay in transient memory and upload only through the authenticated Profile boundary. Review pages are skipped. Background probes a fingerprint before upload; the server compresses only new questions, structures or search recordings and counts repeats. Corrections are unlabelled samples, never automatic gold answers. Independent answer labels and revision-bound AI answer recordings feed offline replay using the real scanner with synthetic identities. Missing or stale recordings are reported explicitly; model recordings are never gold. The normal test/update suite runs the ignored local corpus when present; an absent corpus is an explicit skip. Replay does not establish successful site writes or real-page acceptance.

Each automatic run owns one AbortController. Its AbortSignal reaches the operation context; lifecycle changes, removal, manual navigation and source invalidation cancel the same signal. A cancelled signal cannot be reset by a later review or asynchronous response. Review pauses input listeners while the person intentionally edits, then validates the current operation before resuming.

`formDocument` is a bounded snapshot for model input only. Unrelated page text changes never cancel an answer batch or reset its retry state; each pending answer is checked against its own current field shape before writing. Whole-page text and field snapshots do not enter answer or binding cache keys. Existing field, Profile, saved-answer and job scope still determine reuse.

New pure policy modules are ordinary ES modules and their unit tests import their exports directly. DOM integration fixtures use an isolated browser realm with explicit dependencies; their module loader must preserve the maintained module bodies and import bindings.

The reviewed answer matrix runs both original questions through shared recognition and explicit type inputs through formatters/options; neither may replace the other. Cross-platform DOM regressions verify known answers still write with the answer service offline and only unresolved fields are requested. Provider stubs do not establish model comprehension. Service tests independently verify Profile projection, deterministic precedence, citation validation, protocol and rejection behavior. Real-provider and real-ATS acceptance remain separate.
