# Controlled installed-storage migration

The explicit worker and private UI are implemented and tested with synthetic data. The owner's real Chrome storage has not been read, uploaded or cleaned. No real server backup, installed-package cleanup or production acceptance is implied. The earlier 1,140-test and browser evidence predates this migration implementation.

## Entry and scope

Ordinary startup enumerates known legacy names and byte counts. It does not retrieve legacy Profile/answer values. Bounded reads of mixed `settings`/`configList` detect retired `premiumSettings.responseContext` without exposing its value in status. Missing metadata APIs, old personal sources or an unfinished migration stop autofill. Old `complete` flags are identity evidence only. Routine DocumentStore reads allow only durable settings/mappings and specifically enumerated session answer documents.

The popup links to `migration.html`. Only this exact private TAB from the current build can initiate migration; startup and alarms never run it. The worker loads on demand. A metadata fence pauses normal Profile, answer and settings writes; existing receipt retries and uncertain-submit guards remain available.

Before source capture or cleanup, the worker applies `TRUSTED_CONTEXTS` storage access and enumerates all extension contexts. Exactly the current background worker and requesting migration TAB may remain. Storage access restriction alone does not exclude old trusted views: additional popup, options TAB, side panel, offscreen, devtools or unknown contexts block work. The user saves/closes them. Application pages receive the existing stop/invalidation message without navigation or refresh. This exclusion plus current-build write fencing addresses the absence of atomic Chrome compare-and-delete.

## Protocol and recovery

1. An authenticated Profile grant binds each session to device, build and exact manifest. Sources upload serially. Each value is encoded once as `JSON.stringify(value)` UTF-8 with exact size/SHA-256. `manifestText` retains original bytes; Chrome object-member reordering is handled only in redundant metadata comparison. The server rejects duplicate JSON keys, NaN, unknown structures and credential-bearing content, preserving the source.
2. The private vault stores exact originals under restricted filesystem permissions. No new encryption/key system is claimed. Durable per-file copies, restore hash checks, client/server manifests and full source coverage must all succeed. HTTP success or a client completion flag cannot authorize cleanup. Unresolved backups stay pinned within bounded retention/capacity limits.
3. Domain reconciliation compares facts, answers, applications and contexts with server versions. Choices are server-issued. A value-changing choice needs a complete bounded preview showing source and current values; text is chunked, attachments expose only exact base64-text SHA/byte count. The final token binds full pagination, source fingerprint, target version and plan revision and is rechecked on resolve. Private values remain only in the migration TAB's memory, never local journal/logs. Incomplete over-budget previews cannot authorize a choice.
4. Approved operations use server idempotency and version checks. If a reply is lost partway through apply, the same plan revision resumes before verifying every domain operation. It cannot skip directly from a partially applied plan to cleanup.
5. Every removal requires a short-lived permit bound to device, migration/build, backup, selector and source hash. Immediately before mutation the worker checks all remaining selectors/hashes, contexts and target. New/changed sources halt cleanup. A metadata-only intent precedes one-key deletion; verified readback then produces an ACK. Lost ACKs resume without replaying deletion.
6. Mixed settings remove only the approved own property. Whole-container before/after hashes chain across preset leaves and preserve all other settings/array indexes. Whole-storage `clear()` is forbidden. Server completion and an empty demonstrated inventory release the fence.

Pending session answers never move into local storage. Private-cache release first safely writes the retained BASE subset and excludes retained response keys from removal. A failed retention write leaves the original pending values intact. Browser exit may naturally erase session storage: a missing entry that lacked durable upload is an error; after backup/restore/domain proof, a distinct `session_expired` authorization records observed expiry rather than inventing a deletion intent. Absence is rechecked after the permission request.

Changed builds cannot reuse old permits. The explicit page can inspect metadata and supersede a paused session, preserving its previous backup. Capacity exhaustion blocks supersession while retaining the source.

## Limits and evidence

The shared contract bounds one entry to 8 MiB, a session to 128 MiB/1,000 entries/2,000 operations, JSON depth to 64 and total nodes to 1,000,000. It permits one active/four retained sessions per device, one global admission slot, 512 MiB vault storage including temporary copies and requires 256 MiB free space. Preview pages are at most 32 KiB/20 rows; total preview is 256 KiB/200 rows. HTTP timeout is 20 seconds. Exceeding limits preserves sources.

- `tests/storage-migration.test.mjs`: exact serial upload, offline/restore failure, conflicts, extra trusted views, changed sources, lost ACK, container hash chain, local/session separation, expiry before/after backup, interrupted start/apply, build changes and Chrome object reordering.
- `tests/migration-ui.test.mjs`: complete preview requirement, source/current rendered safely as text, incomplete over-budget choice blocked.
- `tests/private-session-lifecycle.test.mjs`: retention failure cannot lose unuploaded answers; retained keys never deleted.
- `services/jobs-radar/tests/test_storage_migration_client.py`: actual Node worker with authenticated ASGI bridge and synthetic local/server/session domain reconciliation; worker is not mocked.
- `scripts/verify-migration-browser.mjs`: isolated real Chromium, synthetic previous package/storage, current package replacement, trusted-view block, interruption/offline resume, private preview/confirmation and scoped cleanup. Public HTTPS is blocked and worker HTTP uses synthetic responses. `.qa/migration-browser-*` records evidence; this is separate from the real-service bridge.

## Retirement

This is one-time explicit migration tooling, never a legacy facts source for ordinary filling. After supported installations verify migration and their recovery period is agreed, disable new service migration sessions and remove the migration TAB/worker/transport/popup link from normal builds. Retire the startup fence only when old installations are no longer accepted. Keep contract fixtures, offline restore tools, archive verification and nonpersonal receipts. Synthetic success alone is not permission to retire recovery or the installed-upgrade guard.

## Operator sequence for the existing installation

This checklist is prepared, not executed. On 2026-09-26, the fixed directory's manifest reads `2.28.0 / b6c10d733d20ddf6`. That proves the files on disk, not which version Chrome currently has loaded. Native candidate `a75996fe6867ac59` passed 1,208 tests, the isolated migration browser's five scenarios and the native browser's nine scenarios before the subsequent explicit recovery-pause fix. A new staged build and its targeted browser evidence must replace that candidate before installation. Do not rebuild or reload in the middle of a migration.

1. **Wait for the coordinated service release.** The root operator first verifies the controlled workspace/database/attachment backups and matching production service, website, protocol 2 and migration routes. A workspace backup is separate from this browser migration vault. No old storage is removed on the strength of either a health check or a package build.
2. **Stop the old pages before replacing their worker.** Inventory live application frames without reading their field values. Use the old queue's pause command for tracked pages, then collect a stop acknowledgement from each remaining live frame through the old worker's supported `jobs:queue-control` message with `state: { owned: true, allowed: false }`. Target the actual frame/document rather than accepting one reply for an entire tab. This withdraws its navigation permission and cancels a running automatic operation. The old build does not understand `jobs:private-session-invalidated`; a new worker does not remove an old content script. A missing acknowledgement is a blocker, not evidence of a stop. Do not refresh or close an in-progress form just to obtain one. A request already sent to the ATS cannot be recalled: retain its uncertain state and investigate the original result before any retry.
3. **Finish pending captures before a reload.** The verified old source saves acknowledged manual-answer captures and the management BASE in `storage.local`; its receipts and queue state are also durable. Wait for actual `memory_saved`/background write acknowledgements for any pending capture, not a fixed delay. A value still only in the page's memory has not been backed up. Enumerate session names/counts before reload; unexpected pending-only sources require investigation. Chrome clears `storage.session` on extension reload/update as well as browser exit, so a native installation with unacknowledged session answers must first complete server synchronization or this migration's durable upload/restore/domain verification. Do not copy them to local storage as a workaround. See the [Chrome storage lifecycle](https://developer.chrome.com/docs/extensions/reference/api/storage).
4. **Install the exact verified native stage at the existing path.** Use `publishPackage` only after reviewing the staged manifest and unchanged extension identity; it preserves the previous directory and restores it if the switch fails. Reuse the current installation and existing connection state, then reload that same extension once. Do not uninstall/reinstall, create a second extension identity, or manufacture a new grant in a bundle. Record both the disk build and the running worker's build. Previously open application pages remain paused; only a deliberately fresh authorized page may start the new runtime later.
5. **Restore the existing account authorization if required.** Existing device/grants remain in `jobsSyncV1`. If expired, open the owner's authenticated jobs website: the existing site bridge requests `/api/extension/connect` for the same device and extension with `profiles: true`, then passes the tokens directly to the worker. Do not paste or log them. A changed grant must prove access to every pending answer's original Profile; an ownership mismatch keeps the drafts and refuses the connection change. The ATS login account is separate and remains untouched.
6. **Open the explicit private migration tab.** Choose **旧资料迁移** in the popup, then close the popup and other extension views. Leave the authenticated website open if needed, but no other extension TAB/side panel/offscreen/devtools view may remain. Click **备份并核对旧资料**. The worker freezes normal writers, stops current native page sessions, uploads serially and verifies restore bytes before presenting a plan. Log only migration/device/build identities, hashes, counts, phases and error codes. Do not copy the private differences into a report.
7. **Resolve facts explicitly, then verify server application.** For each conflict, load all pages of **查看差异** and confirm the actual source/current difference; Profile ownership, conflicting answers and retired settings context cannot be inferred from a preset name. Attachments show exact base64-text hash/size, not their contents. Unknown facts remain `required_input`; proceed with independent conflicts only. **保存已确认的差异** resumes the same idempotent plan if a reply is lost. Only `ready_to_clean` means every operation and the backup restore proof were verified.
8. **Clean only permitted sources and read back completion.** Use **核验后清理旧缓存**. Each operation rechecks writer exclusion, source/whole-container hashes and its permit, then verifies absence or the exact permitted single-path rewrite before ACK. A changed source, expired permit or unavailable service stops cleanup. Reopen the migration status after completion and require server `complete`, matching build/manifest/backup proof, all cleanup ACKs, local complete journal and `JobsStorageUpgrade` state `ready`. Compare before/after metadata or in-memory equality checks to show pending receipts, uncertain submission guards, operational account settings and unrelated settings were preserved; do not print their values. If the server legitimately acknowledged an outbox item, verify its same event ID/state rather than expecting a fixed queue length. Unknown keys are an explicitly unverified scope, not a claim that all browser privacy data was erased.
9. **Perform the coordinated acceptance, then retire explicitly.** Confirm the server Profile and attachment readback/recovery, correct Profile identity on a fresh representative page, stale-operation rejection, no automatic retry of an uncertain submission, independent redacted diagnostics and no unsolicited full-page upload. Reuse the recorded fixed performance and reproduction evidence; do not make a new submission to manufacture proof. Item 3 still needs the separate workspace/Git-history cleanup. After all supported installations are accounted for, no migration is unresolved and the recovery period is agreed, remove online session creation/routes and the isolated migration UI/worker/transport from a later reviewed release. First preserve nonpersonal receipts, exact-source recovery archives and offline restore tools. The old-client rejection and startup guard stay until old installations are retired. This removal is a coordinated release action, not an automatic side effect of one browser's `complete` flag.

During a restricted service recovery, only HTTP 503 with `code: recovery_application_pause` triggers the shared private-session invalidation path. It stops native pages, drops active Profile references and keeps pending answers, receipt outbox and submission guards. Generic 503/HTML failures retain their ordinary retry behavior. Resume requires a fresh authenticated operation after the service returns; a recovery reply cannot undo an already dispatched ATS request.

This acceptance does not rewrite the timing of the baseline or replace behavior/installed-version evidence.
