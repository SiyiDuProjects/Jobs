# Jobs Workspace

Private workspace: this Jobs repository, including from a worktree. Resolve paths from the current checkout and host environment; never assume a drive letter, username or operating system. Never publish personal data or store passwords/verification codes. Current personal facts and application attachments belong to the server Profiles. Local recovery archives are not a runtime fact source.

## Development and application work

This is a development workspace that is also used for applications. Follow the user's current task. For code, architecture or documentation work, read the relevant implementation and evidence; do not routinely fetch personal Profiles or load application handoffs, old ledgers or benchmarks.

For an actual application run, use the installed `jobs-apply` skill. Resolve its `SKILL.md` from the session's skill catalog or `$CODEX_HOME/skills/jobs-apply/SKILL.md` (default Codex home: `~/.codex` on the current host). It owns the operational workflow: get jobs through the native Jobs tools, open them in the requested browser, let the extension run and handle remote AI review. The interface reference is `notes/jobs-radar.md`. Editing the skill or workflow never starts or resumes applications by itself. Preserve any live form already in progress.

When a specific investigation needs a personal fact, obtain it from the application's bound server Profile with native `get_profiles`; keep it in memory only while needed. The contract excludes credentials and attachment binary data. Missing access is a blocker, not a reason to reconstruct facts from recovery archives. Later user corrections win. Keep unknown answers and new commitments unresolved.

## Record actual bugs, not routine applications

For an unsupported component, incorrect write, lost value, failed continuation or another concrete bug, the agent owns a focused diagnostic case using `notes/application-ui-repairs.md`, even when the plugin reports no error. Capture enough structure and behavior to reproduce it; redact personal answers and secrets. Group the index in `notes/ats-platform-status.md` by ATS, with company scope, priority, status and a case link. Shared extension/service defects have one shared case referenced by affected platforms. Reuse confirmed matching cases; record new occurrences and affected companies, and link merely similar symptoms as possible duplicates until their mechanism is known. Prioritize incorrect critical answers/duplicate submissions, then blocked flows and recurring multi-company defects, then nonblocking issues. Capture before repair where possible, then continue applications; do not turn the run into a code investigation or refresh/resubmit to obtain evidence.

## Changing the autofill code or the service

- **Explain before changing.** For a wrong or missing fill, first read the current redacted diagnostics from `get_browser_history` detail (or the diagnostics page). Inspect the available field `decision`, `trace` and structural evidence to identify the responsible layer. Any displayed `value`, answer or option text may be synthetic or redacted; it is not a promise of access to the person's original answer. Read authorized facts from the bound server Profile when needed, and never copy raw personal answers into diagnostic evidence. Fix the layer supported by that record.
- **A missed control** appears in the snapshot's `unrecognized` list (question, reason, tag/role/class outline) and as a local reproduction case. Make it readable in its layer: a site's structure in `src/custom/platform-config.js` declarations, a widget as a registered component (`describe`/`facts`, `readOptions`, `choose`) in the `control-fields.js` registry; standard ARIA comboboxes already use the fallback. Never add site branches to the scanner; all page clicks/events go through `JobsPageActions`.
- **Every adapter** (all 30 in `source/content/adapters/`) runs each page/step as one `JobsAutomatic.advance({fill})`. Adapters provide structure actions and ordered `JobsFormPipeline.bind` declarations (`name/find/answer`, `answers`, `checked/replace`, `after`) only; they never write answers, read options or call a resolver (`tests/one-answerer.test.mjs` checks every adapter). Sign-in fills use `jobsFillAccount` outside a run; step buttons come from `jobsStepNavigation`. Inside the run each binding is written in page order, then every remaining empty node is resolved at most once, conditional fields settle/rescan, then required-only AI, review and navigation. A run keeps one field ledger (`JobsFormPipeline.ledger`: state, decider, confirm, card); every answer (binding, rule, AI, review card) reaches a field only through `JobsFormPipeline.write` (claim → write → kept by the page → decide or abstain), and a failure changes only that field's record. Optional fields accept only Profile or `saved_exact_question`. A canonical node has one automatic decider per run (the layer whose value it holds); a second claim must diagnose and fail. A binding or rule that cannot match or keep its value abstains; a required choice then gets an AI answer the person must confirm. Filling defaults (`JobsProfileAnswers` `defaults`) rank below Profile facts and the person's saved answers. `JobsFormPipeline.answered(root)` provides binding/rule nodes excluded from saved manual responses. Option writes use `optionSpec` through the sole `chooseSpec -> chooseFrom` transaction. Waits are conditions (`JobsFormPipeline.settled`, bounded `JobsDOMWait.until`), never fixed delays; an unconfirmed upload returns a hold and does not navigate. A new ATS is added the same way.
- **One rule layer.** What a field means, which option it takes and what to search for: `src/custom/profile-answers.js` (topic specs such as `degreeSpec`, and `schoolSpec`/`locationSpec` with their search terms) and `src/custom/option-match.js`. Which answer a question gets (Profile rule or the person's saved answer, with its reason) is decided once in `src/custom/answer-resolver.js` (`JobsAnswerResolver`). Components open, search one term, list, click and read back; they never read the Profile. The shared entrance tries each search term, and a component reports page-structure facts such as an entry's `educationIndex`. Adapters may not introduce answer decisions; answer and option policy stays in the shared rule layer.
- **Behavior tests** protect every adapter and component; the historical comparison with the original bundle was retired on 2026-09-24.
- **Deliver local extension fixes.** A requested fix includes updating the existing local installation: after editing, run `npm run update` in `extensions/speedyapply-local`. It checks the combined source, builds the private package and replaces the fixed `dist` with rollback protection. Do not stop at `npm run build` (candidate only), copy files into `dist`, or directly publish an old candidate. Report a blocked check explicitly rather than calling the fix delivered. Updating local `dist` is part of the authorized repair; it is not a server/store release. Preserve live forms and tell the user to reload the extension; disk update, browser reload and real-page acceptance remain separate evidence.
- **Parallel fixes share one delivery.** Coordinate overlapping edits; integrate worktree changes into the primary checkout before delivery. One agent runs `npm run update` after the participating edits settle. Other agents must not publish their own candidates or remove an active update lock. If source or installed-package checks detect concurrent changes, inspect the change and rerun the full update from the combined source. Tests cannot prove that an unmerged or overwritten source edit was retained; verify the participating fixes before delivery.
- **Service releases** only through `services/jobs-radar/deploy/release.sh` from a committed tree (`--build` to stage, `--rollback` to restore the previous image). Never copy single files to the server.
- Architecture, migrated/retained scope and acceptance: `notes/archive/autofill-architecture-2026-09-23.md`.

## Files used only when needed

`notes/ats-platform-status.md`: compact platform-grouped bug index. Keep one short row per issue with priority, status, company scope and its existing diagnostic link. Preserve user-confirmed working flows; fixed code awaiting real-page verification stays open. Details and deduplicated occurrences belong in the linked case. Read only when relevant.

`notes/jobs-radar.md`: native interfaces, remote review and transport questions. `notes/application-handoff-current.md`: stopped application state, read when applying or investigating that run. `notes/application-ui-repairs.md`: a specific UI failure. Server Profiles: current facts and attachment metadata; private recovery archives are used only for an explicitly scoped recovery task. `notes/benchmark-*`, `notes/archive/radar*`, `.qa/`, `work/`: previous runs, evidence or backups, not startup instructions. The plugin uploads the attachment bound to the selected server Profile; do not reinstate a local resume directory as the normal source. `services/` and `scripts/`: implementation/maintenance.
